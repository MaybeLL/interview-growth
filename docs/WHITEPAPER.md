# 程序员面试能力成长系统：项目白皮书

> 版本：0.1（MVP 决策基线）
> 日期：2026-07-19
> 状态：已确认，可进入实现设计

## 1. 摘要

本项目构建一个运行在 Codex 或 Claude Code 中的本地能力成长系统。用户以自然语言创建目标岗位、收录面试题、参加自适应模拟面试、接受结构化评价，并通过教练练习和无辅助复测逐步关闭能力缺口。

系统并不把聊天记录当作学习档案，也不让模型凭总体印象给出一个不可解释的分数。它把目标岗位标准、题目版本、评价规约、原始作答、多维评价和证据来源全部结构化保存，使每一项能力判断都能回答：依据哪个岗位标准、哪道题、哪次原始回答、哪些具体证据得出。

核心产品循环是：

```text
定义目标岗位标准
    ↓
独立评估与自适应追问
    ↓
识别可追溯能力缺口
    ↓
教练练习与训练处方
    ↓
使用不同题目无辅助复测
    ↓
更新准备状态并继续循环
```

MVP 聚焦程序员求职面试。底层领域模型保留扩展至日语、写作等其他成长目标的可能，但首期不会为通用性牺牲程序员面试体验。

## 2. 问题与机会

现有的 Agent 面试练习通常存在五个问题：

1. 对话结束后，题目、回答和反馈没有形成可查询的长期资产。
2. 不同岗位目标混在同一上下文中，评分标准和学习记录相互污染。
3. 评分依赖模型的临场印象，缺少预先声明的评价规约和证据链。
4. 教学提示后的复述被误认为独立能力，面板容易被“刷高”。
5. 系统擅长指出问题，却没有把缺口转化为练习、复测和关闭条件。

本项目的机会不是再做一个聊天机器人，而是把 Coding Agent 变成一个有明确目标边界、可靠领域状态和可验证成长循环的长期能力教练。

## 3. 产品定位

### 3.1 北极星

帮助用户持续缩小当前能力与目标岗位要求之间的差距，并能够用新的、无辅助的作答证据验证提升。

### 3.2 产品形态

- 单用户、本地优先的 Agent 扩展系统。
- MVP 交付为可在 Codex 与 Claude Code 安装的同一插件包。
- 用户通过自然语言会话使用，不开发独立 Web UI。
- 能力面板以 Markdown 或终端报告呈现。
- Codex 与 Claude Code 通过各自的薄清单适配层复用同一组 Skills、Hook 和 CLI 核心。

### 3.3 设计原则

1. **目标隔离优先**：隔离的是标准、题库、历史和状态，而不只是界面筛选条件。
2. **证据优先于分数**：任何等级都必须能追溯到原始回答和评价依据。
3. **评估与教学分离**：辅助练习帮助学习，但不能直接证明独立能力。
4. **历史不可静默改写**：标准、题目、回答和评价的历史含义必须稳定。
5. **确定性核心、概率性边缘**：模型负责理解与生成；应用核心和结构化 CLI 负责校验、事务和状态。
6. **上下文最小化**：只给当前角色完成当前任务所必需的数据。
7. **先闭环，后平台化**：先证明能力提升，再建设 UI、云端和多宿主能力。

## 4. MVP 范围

### 4.1 包含

- 多成长目标的创建、选择、暂停、结束、归档和物理隔离。
- 从岗位方向、多份 JD 和用户约束生成目标标准草案。
- 目标标准审批、版本化和历史评价追溯。
- 目标内题库、主题树、题目版本、评价规约和搜索。
- 面试与练习过程中自动记录题目、追问、原始回答和评价。
- 用户指定范围、系统自适应选题的模拟面试。
- 面试官、评价者、教练三个逻辑角色。
- 0–4 多维岗位相对评价、证据覆盖、关键门槛和准备状态。
- 评价争议、独立重评和人工裁决。
- 能力缺口、训练处方、教练练习和不同题复测。
- 轻量真实面试复盘。
- 目标级导出、导入、备份、恢复和删除。
- Hook 驱动的检查点、漏写检测和中断恢复。

### 4.2 明确不包含

- 独立 Web／移动端 UI。
- 登录、账户、组织权限、多用户协作或云同步。
- 跨目标共享题库、共享评分或自动复用证据。
- 程序员面试之外的完整垂直场景实现。
- 依赖某一宿主专有 MCP 或模型 API 的能力。
- 完整求职 CRM、职位投递和联系人管理。
- 应用级数据库加密与密钥恢复。
- CLI 或应用核心直接调用模型或持有模型 API Key。
- 未经真实结果校准的 0–100 总体分数。
- 完整 Event Sourcing。
- 通过 Hook 解析任意聊天并猜测领域事件。

## 5. 核心领域模型

完整统一语言见 [CONTEXT.md](../CONTEXT.md)。核心关系如下：

```text
成长目标
├── 目标岗位画像
│   └── 目标标准版本
│       ├── 主题要求
│       ├── 能力要求
│       └── 关键门槛
├── 主题树
├── 能力维度
├── 题库
│   └── 题目
│       └── 题目版本 + 评价规约
├── 评估会话
│   ├── 面试计划
│   ├── 主问题与追问题目
│   └── 作答尝试
│       └── 岗位相对评价
│           └── 维度评价
├── 能力缺口
│   └── 训练处方
└── 真实面试复盘
```

### 5.1 成长目标是最大隔离边界

一个成长目标在 MVP 中通常对应一个岗位方向、级别和侧重点明确的目标岗位画像。例如“高级 Agent Engineer”和“LLM Infra Engineer”应是两个目标；同类岗位的多份 JD 可以共同作为一个目标岗位画像的依据。

每个目标独立拥有：

- 目标标准及其版本；
- 主题与能力模型；
- 题库及题目历史；
- 面试、作答和评价记录；
- 能力面板、缺口和训练记录；
- 真实面试复盘。

跨目标手工复制题目时创建新的独立对象，不保留共享身份或状态联动。

多目标追踪通过注册表提供名称、生命周期和最近活动等独立卡片；查看详细准备状态前必须显式选择目标。MVP 不生成跨目标总分、排名或联合证据视图。

### 5.2 主题与能力维度分离

- **主题**回答“在讨论什么”，例如 RAG、Agent Memory、Kafka。
- **能力维度**回答“用户表现出什么能力”，例如概念准确性、问题拆解、系统设计、权衡分析和表达沟通。

主题在每个目标内形成单父级树，支持规范名称和别名。一道题可关联多个主题，也可考察多个能力维度。主题可以灵活新增；合并会影响历史统计，因此必须由用户确认。

### 5.3 版本与不可覆盖历史

- 目标岗位画像、能力维度和评价规则共同形成目标标准版本。
- 题干或评价规约变化时创建新的题目版本。
- 每次回答创建新的作答尝试，绝不覆盖旧回答。
- 每次重评和人工裁决都新增评价记录。
- 作答尝试固定引用当时的题目版本；评价固定引用当时的目标标准版本。

## 6. 关键用户旅程

### 6.1 创建成长目标

1. 用户提供岗位方向、目标级别、公司类型、时间计划，以及可选的 JD、简历和背景信息。
2. 目标管理 Skill 调用结构化 CLI 创建目标及独立数据库。
3. 宿主 Agent 生成目标标准草案：岗位画像、主题树、能力维度、要求级别、权重和关键门槛。
4. 系统展示假设与信息缺口，用户修改或补充。
5. 用户批准后形成目标标准 `v1`。
6. 标准批准前可以收题和练习，但不能产生正式准备度证据。

### 6.2 在普通会话中收题

1. 用户明确表达“记录／收录这道题”的意图。
2. Question Bank Skill 搜索当前题库、主题名称和别名，提示明显重复。
3. CLI 保存待完善题目。
4. 宿主 Agent 生成主题映射、能力映射和评价规约。
5. CLI 校验规约完整性，生成可评估题目版本。

普通问句默认不入库；意图不清时必须先确认。

### 6.3 开始模拟面试

1. 用户选择当前成长目标并提出面试范围或时长。
2. Interview Skill 创建面试计划，补全未指定的难度、题量和题源策略。
3. 系统按以下优先级选择主问题：
   1. 未通过的关键要求；
   2. 证据不足或低置信度领域；
   3. 当前薄弱项；
   4. 长时间未验证的领域；
   5. 随机覆盖。
4. 主问题优先来自题库；覆盖不足时，先生成规约并入库，再提问。
5. 用户回答后，Skill 立即保存原始作答，再调用评价者流程。
6. 面试官根据回答生成实质性追问。追问在提出前作为一等题目保存。
7. 评估结果在后台记录，按计划在题后或整场结束后反馈。
8. 面试结束时生成复盘、能力缺口和下一步训练建议。

### 6.4 教练练习与复测

1. 用户选择能力缺口或接受系统推荐。
2. 教练解释缺漏，提供提示、例子和结构化练习。
3. 所有受辅助回答保存为辅助练习记录，不计入岗位准备度。
4. 系统安排使用不同题目的无辅助复测。
5. 新证据达到等级与覆盖门槛后，能力缺口才关闭。

### 6.5 真实面试复盘

系统轻量记录公司、岗位、轮次、时间、回忆题目、回答大意、面试官反馈和轮次结果。回忆题目进入当前目标的题库候选；回忆回答默认是低置信度材料，不进入准备度计算。真实结果用于发现模拟覆盖盲区和长期校准系统判断。

## 7. 评价体系

### 7.1 岗位相对评价

评分只表达“相对于当前目标岗位标准的达标程度”。同一回答在中级岗位可能达标，在高级岗位可能不达标，因此分数不能跨成长目标比较。

### 7.2 达标等级

| 值 | 含义 |
|---|---|
| `N/A` | 尚无相关证据或本题未考察，不能判断 |
| `0` | 已作答，但存在根本性错误或没有展示相关能力 |
| `1` | 明显低于岗位要求，关键知识或推理大量缺失 |
| `2` | 接近要求但仍有重要缺口，无法稳定通过 |
| `3` | 达到目标岗位要求，回答正确、完整且可解释 |
| `4` | 明显超过要求，能深入分析边界、权衡和延伸问题 |

`N/A` 不存为数值 0。每项维度评价必须同时包含：

- 支持该等级的原回答证据；
- 关键缺漏或错误；
- 改进建议；
- 评价置信度；
- 评价者、宿主、模型及提示版本等可获得的来源信息。

### 7.3 评价规约

正式计分的题目版本必须预先拥有完整评价规约：

- 题目意图；
- 预期证据；
- 常见错误和致命缺漏；
- 关联能力维度及重要性；
- 0–4 等级锚点；
- 合理的深挖方向。

评价者不能在看过回答后修改规约来迁就结果。

### 7.4 证据资格

进入岗位准备度的证据必须满足：

- 来自无提示、无参考答案、无即时纠正的独立作答；
- 引用当前目标标准版本，或已经按当前标准新增重评；
- 评价未处于未解决争议；
- 评价置信度达到最低门槛；
- 记录完整且可追溯。

受辅助回答、真实面试后的回忆、无规约题目和低置信度评价默认不合格。

### 7.5 当前水平与覆盖度

默认确认一个主题或能力达标至少需要：

- 3 次合格独立作答；
- 覆盖至少 2 道不同题目；
- 至少 1 次证据来自最近 30 天。

当前水平只取每道题最新的合格证据，按近期性和置信度进行稳健聚合。MVP 优先采用加权中位数，避免一次异常成绩或重复刷题扭曲结论。旧证据保留在历史趋势中；最近 30 天没有证据时标记“需要重新验证”。

具体时间权重作为可配置策略实现，首期通过测试数据和四周试用校准，不写死为不可迁移的领域事实。

### 7.6 要求与关键门槛

目标标准将要求分为：

- **关键要求**：未达到等级或覆盖条件时，准备状态不能为“已准备好”。
- **核心要求**：高权重参与总体判断，允许有限互补。
- **补充要求**：用于识别优势，不阻塞基本达标。

MVP 不展示总体百分制。能力面板以准备状态、关键门槛、证据覆盖和分项等级为主要结论，避免未经真实结果校准的虚假精确感。

### 7.7 评价争议

用户可以标记评价有争议并说明原因。有争议评价暂不参与当前准备度。用户可以触发不读取原结论的独立重评；若规约有误，应先创建新规约版本。最终可接受原评价、接受重评或提交带理由的人工评价。所有结果追加保存，来源透明。

## 8. 能力面板

能力面板不是排行榜，而是一个面向行动的准备度报告。

### 8.1 概览

```text
当前目标：高级 Agent Engineer
标准版本：v3
准备状态：尚未准备好
关键门槛：4/6 通过
证据覆盖：72%
需要重新验证：2 项
未解决评价争议：1 项
```

### 8.2 分项视图

- 主题树各节点的当前等级、覆盖度、趋势和最近验证时间；
- 各能力维度的当前等级、覆盖度、趋势和最近验证时间；
- 每项结论对应的题目、作答证据和评价规约；
- 达到要求、接近要求、明显不足和 `N/A` 的项目分布；
- 未通过的关键门槛。

### 8.3 行动视图

- 按岗位重要性、差距、证据不足和陈旧程度排序的能力缺口；
- 每项缺口的原因与证据；
- 当前训练处方；
- 推荐下一道练习题或复测题；
- 建议复测时间。

## 9. Agent 角色模型

| 角色 | 使用场景 | 可以看到 | 不应看到／不应做 |
|---|---|---|---|
| 面试官 | 正式评估 | 面试计划、当前题目、必要岗位摘要、有限追问方向、当前会话记录 | 完整参考答案、历史总分；不能提示或即时教学 |
| 评价者 | 作答后结构化评价 | 冻结题目版本、完整评价规约、原始作答、辅助标记、必要岗位标准 | 原评价结论；不能参与提问或修改规约 |
| 教练 | 复盘与练习 | 题目、回答、评价、能力缺口和训练目标 | 不能把辅助互动登记为独立作答证据 |

三个角色是逻辑边界，不要求 MVP 使用三个不同模型。宿主 Agent 可以在隔离步骤中切换角色；未来可以通过子 Agent 或独立 Evaluator Provider 获得更强隔离。

## 10. 系统架构

```text
┌─────────────────────────────────────────────┐
│ Codex / Claude Code Host                    │
│  Skills: 目标 / 题库 / 面试 / 教练 / 面板   │
│  Roles: 面试官 / 评价者 / 教练               │
└──────────────────┬──────────────────────────┘
                   │ structured JSON commands
┌──────────────────▼──────────────────────────┐
│ Python CLI + Operation Registry             │
│  Application services                       │
│  Domain invariants                          │
│  Context assembler                          │
│  Read models / aggregation                  │
│  Repositories / migrations                  │
└───────────────┬───────────────────┬─────────┘
                │                   │
       ┌────────▼────────┐  ┌───────▼──────────┐
       │ registry.sqlite │  │ goal-<id>.sqlite │
       │ 最小目标索引     │  │ 单目标领域真源    │
       └─────────────────┘  └──────────────────┘

Hooks ──► 目标绑定校验 / 漏写检测 / 检查点 / 恢复
```

### 10.1 职责边界

**Skill**：定义自然语言入口、角色提示和工作流次序；不执行 SQL，不自行维护持久状态。

**CLI**：唯一 Agent 写入口；接收 JSON、校验操作契约并返回统一结果，不包含模型推理。

**应用核心**：负责领域校验、版本、事务、幂等、查询、聚合和 Context Packet 生成。

**Hook**：确定性的生命周期守卫；负责检测流程断裂，不通过 NLP 猜测业务语义。

**宿主 Agent**：完成岗位分析、题目规约生成、追问、评价和教练反馈等概率性推理。

## 11. Skill 设计

| Skill | 主要触发 | 主要职责 |
|---|---|---|
| `goal-manager` | 创建、列出、选择、切换、暂停或结束目标 | 目标生命周期、当前目标绑定、导入导出入口 |
| `target-standard` | 分析 JD、建立或调整岗位标准 | 生成标准草案、呈现假设、请求批准、创建新版本 |
| `question-bank` | 明确要求记录、搜索、整理或修改题目 | 收题、补规约、主题管理、重复建议和历史查询 |
| `interview` | 开始、暂停、恢复或结束模拟面试 | 面试计划、自适应选题、自动记录、追问和复盘 |
| `evaluator` | Interview Skill 的内部评价步骤 | 生成符合结构化契约的多维评价，不直接面向用户触发 |
| `coach` | 讲解、专项练习、改进回答或执行训练处方 | 辅助练习、反馈、训练记录和复测准备 |
| `capability-dashboard` | 查看能力、进度、短板或下一步 | 展示准备状态、证据、趋势、缺口和行动建议 |
| `real-interview-review` | 复盘真实面试 | 记录真实题目、反馈、结果并发现覆盖盲区 |

所有写工作流都应显式调用结构化 CLI。Skill 可以隐式触发，但题库写入在普通聊天中仍要求明确的用户收录意图。

## 12. CLI 接口设计

CLI 操作应以领域动作命名，不暴露通用 SQL 或低级数据库接口。Agent 使用
`interview-growth call <operation>`，在标准输入中传入一个 JSON 对象，并接收稳定的
`{ok,data,error}` JSON 信封。使用 `interview-growth operations <operation>` 可查询参数与输出契约。

### 12.7 CLI 约束

- 每个写操作必须验证当前成长目标身份。
- 每次写入携带幂等键和预期版本，防止重试重复和并发覆盖。
- CLI 返回结构化结果、创建的记录 ID、实际版本及下一步允许动作。
- 删除、合并、标准批准等高影响操作要求显式用户确认。
- CLI 不提供任意 SQL、绕过目标绑定的写入或模型调用操作。

## 13. Context 管理

### 13.1 唯一真源

SQLite 是唯一领域真源。聊天历史、Markdown 报告和缓存均不可作为恢复业务状态的唯一依据。

### 13.2 Context Packet 结构

每个 Packet 至少包含：

- `goal_binding`：当前目标与数据库身份；
- `task`：本次操作及允许动作；
- `standard_summary`：必要的岗位标准片段；
- `payload`：题目、回答、评价或面板片段；
- `role_policy`：当前角色可见字段和行为限制；
- `provenance`：来源记录 ID、版本和生成时间；
- `budget`：上下文预算及裁剪说明。

### 13.3 分层加载

1. **全局层**：目标注册表和当前目标绑定。
2. **目标层**：岗位画像摘要、当前标准版本、关键规则。
3. **任务层**：完成当前任务所需的题目、证据或计划。
4. **角色层**：按面试官、评价者或教练删除不应见字段。
5. **会话层**：当前面试状态、待评价作答和检查点。

### 13.4 压缩与恢复

上下文压缩前，Hook 检查活动面试并写入检查点。压缩后通过 CLI 重新获取当前目标和会话
Packet。任何可生成的 Markdown 快照都允许删除并重建。

## 14. Hook 设计

MVP 仅依赖 Codex 与 Claude Code 共有的命令型 Hook 基线，避免把业务正确性绑定到特定宿主
的 prompt、agent 或工具级 Hook。两端共享 `hooks/hooks.json`，并使用双方兼容的
`CLAUDE_PLUGIN_ROOT` 定位已安装插件。

| 生命周期 | 守卫行为 |
|---|---|
| `SessionStart` | 检查插件数据目录和数据库版本；恢复本线程已有绑定，不自动选择全局默认目标 |
| `PreCompact` | 检查待落库作答、待评价记录和会话检查点 |

Hook 不负责：

- 识别任意聊天文本是否为题目；
- 从自由文本推断当前目标；
- 生成评分或训练建议；
- 绕过 CLI 和应用核心直接写 SQLite；
- 将完整对话复制到日志或上下文。

## 15. 数据架构

### 15.1 文件布局

```text
APPLICATION_DATA/
├── registry.sqlite
├── goals/
│   ├── <goal-id>/goal.sqlite
│   └── <goal-id>/goal.sqlite
├── exports/
└── recoveries/
```

插件代码目录只读，用户数据目录可写并跨插件升级保留。

### 15.2 注册表

注册表只保存：目标 ID、名称、生命周期、数据库位置、模式版本、创建和更新时间，以及当前会话绑定所需的最小信息。它不保存题库、能力评分或回答内容。

### 15.3 目标数据库建议表族

| 表族 | 主要内容 |
|---|---|
| `goal_*` | 目标元数据、来源材料和生命周期审计 |
| `standard_*` | 标准草案、已批准版本、能力维度、岗位要求和门槛 |
| `topic_*` | 主题树、别名和合并历史 |
| `question_*` | 题目身份、题目版本、评价规约、主题和能力映射 |
| `session_*` | 面试／练习会话、面试计划、题目顺序和检查点 |
| `attempt_*` | 原始作答、辅助状态、来源和题目版本引用 |
| `evaluation_*` | 岗位相对评价、维度评价、来源、争议和裁决 |
| `practice_*` | 辅助练习、训练处方和复测安排 |
| `real_interview_*` | 真实面试复盘、问题回忆、反馈和结果 |
| `system_*` | 幂等键、迁移记录和审计日志 |

### 15.4 一致性策略

- 打开连接时启用 `PRAGMA foreign_keys = ON`。
- 使用 WAL、合理的 `busy_timeout` 和短事务。
- 一次领域动作在单个事务内完成。
- 原始作答先于模型评价持久化；评价失败不会丢失回答。
- 唯一约束和幂等键防止 Agent 或宿主重试产生重复记录。
- 当前面板和能力缺口是可重建读模型，可按需缓存。
- 每次数据库迁移前创建可恢复备份，并测试从旧版本逐级升级。

## 16. 状态模型

### 16.1 目标生命周期

```text
配置中 → 进行中 ⇄ 暂停
              ↓
            已结束 → 已归档
```

系统只派生准备状态，不自动推进目标生命周期。

### 16.2 题目状态

```text
待完善 → 可评估 → 已停用
   │         │
   └─可练习─┘
```

题干或规约变化创建新版本，不修改历史版本。

### 16.3 面试状态

```text
计划中 → 进行中 ⇄ 已暂停 → 已完成
               └────────→ 已中止
```

每个进行中会话维护待回答、待评价和已完成题目的检查点。

## 18. 安全与隐私

- 数据默认只保存在本机，不自动上传或同步。
- 产品不采集遥测。
- 数据文件仅允许当前操作系统用户访问。
- 数据库不保存模型 API Key、OAuth Token 或其他秘密。
- CLI 只向宿主 Agent 返回完成当前任务所需的最小 Context Packet。
- 文档明确告知：发送给宿主 Agent 的内容仍受相应模型提供商的数据处理规则约束。
- 用户应启用 FileVault、BitLocker 等操作系统磁盘加密。
- 导出操作显式发生；导出包包含 SQLite 和可读 JSON／Markdown 清单。
- 删除目标前提示备份与不可逆后果；系统不承诺清除操作系统或外部备份中的副本。
- 应用级加密和密钥恢复属于后续版本。

## 19. 可靠性与测试

### 19.1 必须覆盖的领域不变量

- 一个领域记录只能属于一个成长目标。
- 一段 Agent 会话最多绑定一个当前目标。
- 未批准目标标准不能产生正式计分证据。
- 无评价规约题目不能产生正式计分证据。
- 辅助练习不能进入准备度。
- 历史作答、评价和标准版本不能原地覆盖。
- 关键要求未通过时准备状态不能为“已准备好”。
- 有争议评价不能进入当前聚合。

### 19.2 测试层次

- **单元测试**：聚合、门槛、版本、状态机和资格判定。
- **属性测试**：重复写入幂等、排序稳定、目标隔离和聚合边界。
- **数据库集成测试**：事务回滚、外键、WAL、迁移和备份恢复。
- **CLI 契约测试**：操作 schema、错误码、版本冲突、stdin 输入和结构化输出。
- **工作流测试**：创建目标到面试、评价、训练、复测的完整链路。
- **崩溃恢复测试**：回答落库后评价前中断、压缩中断、Hook 失败。
- **Context 泄漏测试**：面试官不得看到答案与历史总分，目标之间不得串数据。
- **评价基准集**：固定题目、规约和回答样本，检查重复评价通常保持相同或相邻等级。
- **平台契约测试**：Codex 与 Claude Code 清单分别校验，并运行同一组核心场景。

## 21. 验收与产品验证

### 21.1 工程验收

- 至少两个目标可以创建、切换并证明无数据串写。
- 标准、题库、面试、评价、面板、训练和复盘完整跑通。
- 面试题目、原始回答、评价和追问正常自动落库。
- CLI 重试不产生重复记录。
- 会话中断和上下文压缩后可以恢复。
- 每个分项等级可追溯到标准、规约、回答和评价来源。
- 评价基准集中，同一回答重复评价通常保持相同或相邻等级。
- 用户不需要频繁手工修复漏记、错记或串目标数据。

### 21.2 四周产品验证

- 用户至少关闭一个关键能力缺口。
- 提升由不同题目的无辅助复测证明，而非原题复述。
- 用户认为大部分训练建议具体且可执行。
- 真实面试复盘中新出现的系统覆盖盲区逐渐减少。
- 面板能够稳定回答“为什么尚未准备好”和“下一步练什么”。

工程验收通过表示系统可用；出现可复测能力提升才表示产品假设得到初步验证。

## 22. 主要风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 宿主模型评价波动 | 当前等级不稳定 | 强制规约、结构化证据、置信度、基准集、争议和重评 |
| 自动生成规约质量差 | 错误标准被系统化 | 规约完整性校验、用户可审阅、版本化、低置信度不计分 |
| 主题持续碎片化 | 面板失真 | 规范名称、别名、重复建议、用户确认合并 |
| Skill 漏调用 CLI | 回答或评价丢失 | 原始回答优先落库、检查点、PreCompact 守卫、恢复测试 |
| Context 串目标或泄漏答案 | 评分污染 | 物理数据库隔离、单会话单目标、角色 Packet、泄漏测试 |
| 用户背题刷分 | 虚假掌握 | 每题只取最新证据、至少两道不同题、不同题复测 |
| 证据长期陈旧 | 面板高估当前水平 | 近期性权重、近 30 天证据门槛、重新验证状态 |
| 插件首次安装依赖网络 | 安装失败 | 锁文件、清晰诊断、后续评估预构建环境或打包方案 |
| CLI 参数或输出漂移 | Skill 调用失败 | 可查询契约、Pydantic 校验、统一错误信封和 CLI 契约测试 |

## 25. 决策结论

本项目的 MVP 不是一个“会提问的聊天模板”，而是一套以成长目标为隔离边界、以结构化证据
为事实基础、以 Agent 角色为交互能力、以应用核心和结构化 CLI 为确定性执行层、以 Hook
为可靠性守卫的面试能力成长系统。

首期成功的判断标准不是功能数量，也不是一个漂亮的总分，而是用户能否在不同题目的无辅助复测中，可靠地关闭与目标岗位相关的真实能力缺口。
